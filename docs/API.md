# LayoutKit · 0.1.0

A headless source model and explicit extension catalog for the native Buoy layout editor. Requires EditorKit. Import `layoutkit.LayoutDocument` for `LayoutDocument`, `LayoutNode` and `LayoutProperty`, and `layoutkit.LayoutCatalog` for catalog descriptors and extension interfaces. Buoy 0.72 rejects selective imports of these classes/interfaces; there is no self-named module for bare `Import layoutkit`.

`LayoutDocument(sourceText, version)` is an immutable snapshot. `Nodes`, `FindNode`, `FrameEdits` and `PropertyEdits` inspect source or propose half-open UTF-8 `EditorEdit` ranges. The host keeps the authoritative `EditorDocument`, compares the snapshot version with its current revision, and applies the entire batch once. It then reloads a fresh snapshot. Node IDs belong to a snapshot; resolve them again after source changes. Undo, redo, saved baselines and disk persistence belong to the host.

`DeclarationStartByte(nodeId)` returns the declaration line's UTF-8 byte offset
for diagnostics, including read-only nodes. IDs remain opaque. Shared
`layoutkit.LayoutRelations` measurements and edit planners supply optional
relational snapping, alignment and equal-gap distribution; see
[GUILintKit](https://github.com/BuoyBay/guilintkit/blob/main/docs/API.md#shared-designer-measurements).

The model edits literal `Frame = (x, y, width, height)` assignments and supported scalar property literals. Computed geometry and ambiguous regions remain read-only. Constraint-controlled frames cannot be dragged, while the structured constraint commands can inspect, insert, update and remove supported anchor expressions. Unrelated opaque property expressions are preserved for inspection and are never evaluated. Comments, unknown values, whitespace and code outside changed token spans remain in the original source; the model does not regenerate a file from a reduced schema.

`InsertControlEdits(parentId, typeName, name, x, y, width, height, properties, importName)` inserts a control into a root or supported View. Properties are JSON scalar **values**, not raw source expressions. The compiler currently requires an unqualified Control type, so package controls use a validated source import plus their bare class name. `SourceImports()` returns token-aware basic unconditional imports. `catalog.FindSource(typeName, imports)` resolves discovered controls through those imports and refuses ambiguous matches; canonical package identities remain separate from source spelling.

`Constraints(rootId)` returns structured constraint records. `ConstraintEdits(rootId, constraintId, leftNodeId, leftAnchor, relation, rightNodeId, rightAnchor, offset, priority)` inserts when the constraint ID is empty and updates otherwise. An empty right node selects a numeric constant; `safearea` selects the root SafeArea. `DeleteConstraintEdits` removes one constraint. Node relationships, anchor compatibility, integer offsets and priorities are validated against supported compiler syntax. Unsupported expressions are preserved and remain read-only.

`RenameControlEdits` and `DeleteControlEdits` operate on the layout declaration and its constraint references only. For application commands, import `layoutkit.LayoutRefactor` and use `LayoutProjectRefactor.PlanRename` or `PlanDelete` over the **complete project source closure**, including unsaved buffers and unopened local code-behind files. Plans contain original UTF-8 spans and expected revisions for every changed buffer; hosts must apply all changes atomically. The planner updates proven derived-class handlers and typed receivers, rejects ambiguous references or shadows, and prevents deletion with live references. It cannot account for omitted files. Hosts that cannot establish complete source coverage must disable project refactors rather than claim safety over a selected file alone.

### Arrangement, clipboard and container planners

All planners below return edits against the snapshot's `Version`; the host applies each batch atomically and reloads. They never execute source, preserve comments and unrelated bytes, and throw `InvalidArgumentException` with a user-facing message (for example "Select at least three controls to distribute" or "Controls must share a container") when a command does not apply. Coordinates are parent-relative: a control inside a `View` is measured from that View's top-left corner, and the root's own `Frame` contributes only its width and height (its x/y is the window position).

`layoutkit.LayoutRelations` (shared functions on `LayoutRelations`):

- `AlignToEdits(document, ids, mode, reference)` — `mode` is `left|hcenter|right|top|vcenter|bottom`; `reference` is `selection` (bounding box of 2+ siblings), `key` (`ids(0)` stays put) or `parent` (each control within its own container `(0, 0, width, height)`; works for one control and across containers).
- `DistributeEdgesEdits(document, ids, edge)` — 3+ siblings; the outermost controls stay and the chosen edge or center is spaced evenly between them.
- `SpaceEdits(document, ids, axis, mode, amount)` — `axis` `x|y`; `mode` `equal` (3+, endpoints fixed), `increase`/`decrease` (by `amount` ≥ 1; decrease stops at touching), `remove` (gap 0) or `set` (gap = `amount`). The first control in axis order stays fixed.
- `MatchSizeEdits(document, ids, dimension)` — `width|height|both`, copied from `ids(0)`; containers may differ.
- `MoveByEdits(document, ids, dx, dy)` — nudges; a control whose ancestor is also selected moves only with that ancestor.
- `FramesEdits(document, ids, frames)` — `frames` is a JSON array of `{x, y, width, height}` aligned with `ids` (group drag/resize commits; values are rounded). Each frame is the final parent-relative value for that id; descendants of a listed control are not adjusted.

Arrangement requires editable literal frames in the root or plain `View` containers; hidden (`Visible = False`), computed and constraint-controlled geometry is refused. The older `AlignEdits` and `DistributeEdits` remain.

`LayoutDocument`:

- `ReorderEdits(nodeId, mode)` — `front|forward|backward|back`. Z-order is declaration order among siblings (later is in front). Whole control blocks move together with the `'`/`//` comment lines directly above them; blank lines, container properties and `Constraints` blocks between siblings stay where they are. No edits are returned when the order would not change.
- `CopySnippet(ids)` / `CopySnippet(ids, imports)` — clipboard text: a `' buoy-layout-snippet: 1` header, one `' buoy-layout-import: module` line per recorded import, then the selected blocks (nested children and leading comments included, container indentation removed, LF line endings, declaration order). A selected control inside another selected control is copied once. All controls must come from one root, and every copied property must be a plain literal: computed values, and symbols starting with `Me`/`Super`/`Self` (which could be parenless calls), are refused at copy time. `CopySnippet(ids)` records no imports when every copied type is a built-in control and otherwise records this file's basic imports; pass `imports` (for example catalog `sourceImport` metadata) for an exact list. Constraints are not copied.
- `PlanPaste(parentId, snippet, offsetX, offsetY) As LayoutPastePlan` — inserts the snippet as the front-most children of the root or a `View`. Every pasted name (nested ones too) that clashes, case-insensitively, anywhere in the destination root is renumbered (`button1` → `button2`, `status` → `status2`). Top-level frames are offset; text is re-indented to the destination and uses its line endings; recorded imports missing from the destination are added at the top of the file. A snippet must be a plain list of controls: snippets with code, constraints, container properties, non-literal property values, computed frames, qualified types, radio buttons outside a `RadioGroup` or children under anything but `View`/`GroupBox`/`RadioGroup` are refused. Only unconditional, unaliased imports count as present.
- `PlanEmbed(ids, containerName) As LayoutPastePlan` — wraps same-container controls in a new `Control View` sized to their bounds, placed where the first selected block was; children are re-based to View coordinates and re-indented. An empty `containerName` picks `view1`, `view2`, ... If the selection is not contiguous in declaration order, unselected siblings declared between the selected controls end up in front of the new View.
- `PlanUnembed(viewId) As LayoutPastePlan` — removes a plain `View` (it may set only `Frame`) and moves its children into the View's container at the same position, re-based to container coordinates. Trailing comments on the removed `Control View`, `Frame` and `End Control` lines are kept as standalone comment lines.

`LayoutPastePlan` has `Edits As Array Of EditorEdit`, `Names As Array Of String` (final top-level names, for selecting the result after reloading) and `Imports As Array Of String` (import lines the plan adds, so hosts can show them).

**Code-behind impact of embed/unembed.** A nested control is still a typed member of the lowered window class (see the documentation for `window.md`), so `Me.name`, `With name` handlers and `name_Event` overrides keep compiling after either command. Two things change. Coordinates become relative to the new container, so code that reads or sets `Left`/`Top` sees different numbers. `PlanUnembed` also deletes the View's member, so code that refers to the View itself stops compiling. Before unembedding, hosts should prove there are no such references, for example by asking `LayoutProjectRefactor.PlanDelete` whether the View is referenced. Nested `Constraints` may only refer to a control's own container and its siblings, so both commands refuse (and never rewrite) when a constraint names a moved control or one of its descendants. Radio buttons cannot leave their `RadioGroup`.

The catalog is separate from source parsing. Register a `LayoutControlDescriptor(typeName, displayName, packageName)` and add explicit `LayoutPropertyDescriptor(name, kind, defaultExpression)` entries. Property metadata includes `DisplayName`, `Category`, `EditorId`, `ReadOnly`, `Options`, numeric limits and constructor argument metadata. Validation gates proposed mutations; it does not execute expressions. Unknown property kinds and values can be retained without becoming editable.

**Categories and icons.** `LayoutControlDescriptor.Category` groups controls in palettes. Builtins use `Buttons`, `Text`, `Input`, `Containers`, `Indicators`, `Data` and `Media`. An unset category falls back to the package name, or to `Controls` for the builtin package. `Description` is a one-line summary for tooltips and palette footers. `Catalog.Categories()` returns groups in display order: the builtin groups first, then others in first-registration order. `RegisterBuiltinControls()` registers 20 controls: Button, Checkbox, DisclosureTriangle, Label, TextField, TextArea, ComboBox, RadioGroup, Slider, Stepper, DateTimePicker, View, GroupBox, TabView, PagePanel, ProgressBar, ListBox, ImageView, Canvas and HTMLView. `Splitter` is not registered because the `Control` grammar cannot emit its required constructor argument, but it still has an icon.

Icons implement `LayoutIconPainter.PaintIcon(g As IGraphics, x, y, size, dark)`, a square icon at `(x, y)` with side `size` points. `Catalog.RegisterIcon(typeName, painter)` registers a compiled icon. Types need not be registered controls, so hosts can also theme roots such as `Window`. A later registration replaces an earlier one. `Catalog.IconFor(typeName)` never returns `Nil`. It resolves in this order:

1. A registered painter.
2. For an unqualified builtin type, the builtin `LayoutGlyphIcon`. This vector glyph set also covers layout and root types such as Window, Splitter, RadioButton, StackView, ScrollView and TreeView.
3. For package controls, the `package` glyph.
4. Otherwise, the `generic` glyph.

`HasRegisteredIcon(typeName)` reports whether step 1 applies. The glyphs port the 24-unit `design/iconset` artwork to IGraphics: ink strokes with one accent detail, light and dark palettes, and line widths kept crisp at 16, 20, 24 and 32 pt. Use `New LayoutGlyphIcon(name)` directly for navigator or toolbar icons. Names are normalized, so `control.text-field`, `Text field` and `TextField` all give `textfield`.

Register compiled extensions using `RegisterRenderer(typeName, renderer)`, `RegisterEditor(editor)` and `RegisterEditorView(factory)`. `RendererFor`, `EditorFor` and `EditorViewFor` return `Nil` when absent. A `LayoutRenderer` paints through `IGraphics`; a `LayoutPropertyEditor` can return an expression or cancellation. A `LayoutPropertyViewFactory` returns a native `View`, committing through a revision-bound `LayoutPropertyEditorHost.CommitExpression`. A factory must return `View` because the general `AddSubview(UIControl)` overload is internal.

Native editor Views can implement `LayoutReusablePropertyViewV1.RebindProperty(currentExpression, host)` to reuse their native children across selections and source reloads. Rebind replaces values and callbacks with the fresh host; previously captured hosts must remain expired. This optional contract belongs to LayoutKit so control packages need no dependency on the Canvas editor. Use `kind = "string"` for quoted string choices; `kind = "enum"` accepts qualified symbolic enum expressions.

The host calls `RegisterBuiltinControls()` once. Trusted compiled extensions can register explicitly; data-only package extensions can register automatically from `resources/buoy-designer/plugin.json` (schema `buoy.designer.plugin`, version 1). The host application scans package archives and atomically prepares `.buoy/designer/index-v1.json`; this package reads the data-only index rather than executing package code. The host then calls `New LayoutDiscovery().DiscoverDirectory(PROJECT, freshCatalog)` from `layoutkit.LayoutDiscovery`. Use a fresh catalog on refresh so removed packages disappear. Keep index preparation under the host's control; an opened project must not select an executable discovery script.

Descriptors expose property kinds, defaults and choices, source imports, provenance and bounded declarative rendering recipes. The discovery backend registers interpreted renderers and reusable native choice editors without executing package callbacks, constructors, getters, code-behind or build hooks. Invalid descriptors report diagnostics and do not partially register that package. Reserved source keywords and geometry settings are rejected as scalar property names; ordinary members such as `Locked` and `AnchorStyle` remain valid. Duplicate archive identities within one package root report ambiguity and supply no designer metadata. Local package identities shadow global metadata even when the local descriptor is invalid. Runtime loading of executable plugins and compiler-driven reflection are separate capabilities; packages still declare the design settings they expose. Compiler `@ControlSize`/`@ControlIcon` attributes do not replace the metadata resource.

**Plugin icons and grouping (data only).** A `plugin.json` control may declare the following optional keys:

- `"category"`: palette group, up to 64 characters.
- `"description"`: one-line summary, up to 256 characters.
- `"icon"`: either a builtin glyph name (`"control.status-badge"`) or a recipe object `{"version": 1, "steps": [...]}`.
- `"iconImage"`: a relative `.png` path inside `resources/buoy-designer`.

Icon recipes use the renderer interpreter and validator, painted into a 24×24 grid that is scaled to the icon size and clipped to it. That shared recipe vocabulary is:

- Operations: `fillRect`, `fillRoundedRect`, `strokeRect`, `strokeRoundedRect`, `fillOval`, `strokeOval` and `text`.
- Fields: `x`, `y`, `inset`, `width` and `height` (explicit size instead of the inset-derived one), `radius`, `lineWidth` (0–64), `size`, `color`, `darkColor` (overrides either conditional color branch when `$appearance` is dark), `elseColor`, `property`, `whenProperty`, `equals`, `prefix` and `suffix`.

PNG icons are data too. They must be at most 64 KiB and 512×512, with a PNG signature and an `IHDR` chunk. The discovery helper copies the image out of the archive into the index as `iconImageData` (base64), so layoutkit needs no ZIP support. `DiscoverDirectory` on an unpacked package loads the file from its resources directly. A missing image is not an error: the helper records a per-package `warnings` entry, and the declarative icon (or the package glyph) is used. Pictures are decoded lazily with `Picture.FromPNG`/`Picture.Load` on first paint. A decode failure falls back the same way. Invalid icon data rejects the whole descriptor atomically, like any other invalid metadata. Discovery registers `LayoutRecipeIconPainter`/`LayoutImageIconPainter` instances through `RegisterIcon`; nothing from the package is executed.

The independently packaged [DesignerWidgets](https://github.com/BuoyBay/designerwidgets/blob/main/modules/DesignerWidgets.bui) supplies `StatusBadge Inherits Canvas`, a renderer, a native tone editor and a compiled `StatusBadgeIcon`; its `plugin.json` also declares a recipe icon, a PNG `iconImage`, a category and a description. The [demo](../examples/layout_designer_demo.bui) registers them explicitly and connects `LayoutEditor` to an authoritative EditorDocument, including undo/redo and an in-memory saved baseline.

Linux GUI consumers require the genuine JPEG ABI 8 library expected by the installed Picture runtime. Configure the native loader for that library's actual installation path when it is outside the system search path.

Scalar insertion accepts an additional `floatingProperties As Array Of String` argument after `properties` and `importName`. Typed hosts pass their Double member names so JSON serialization cannot turn `0.0` into an integer source literal. The palette does this automatically. All geometry writers enforce the same ±16777216 range. Renderer recipes are clipped to their control bounds and restore the caller’s graphics state.
